# skills

The master repository for my Claude Code skills. One plugin (`plugins/yili-skills`) holds every skill; `dev/<skill>/` holds that skill's evals, research and tools, which are not installed.

- Write each skill as a way of thinking, not as rules, checklists or thresholds. A rule misses the case nobody expected and goes stale; the reasoning behind it still applies to a new case. A skill is a hint, not a constraint, so keep it as short and as general as it can be: one general sentence rather than a worked procedure, and one file for each kind of question. When a fix would be a list of signals or a count, write the reason behind it instead.
- The skills record how I think in my daily life and work. They are not fixes for what a model gets wrong, so cut reasoning that a capable model does without being told.
- Write skills in plain English, using the ideas of ASD-STE100 Simplified Technical English as `talk-standard-tech-eng` describes them, not the standard's word list or limits. A skill's words become Claude's words when it talks to me, and a model reads a skill literally, so give each thing one name and each word one meaning. Keep the reasoning connected. Keep terms of art and any metaphor that explains better than plain words. Do not mix Chinese or other non-English words into a skill, its description included; the only exception is a quotation.
- A description hands Claude the question that decides whether the skill applies, and leaves the firing to its judgment. Claude matches a description by meaning, in any language, so an example in a description earns its place only when it marks an edge of the scope that the main sentence leaves unclear, never as another way to say the same request (`dev/routing/RESULTS.md`).
- Each skill answers one question about how I think, and no two skills answer the same one. A skill states what it needs as a question, at the moment and under the condition it arises, and never names another skill; Claude finds the skill that answers it from the descriptions. Each skill body opens with a `**Takes:**` line and a `**Returns:**` line. `python -m pytest dev` checks this.
- No skill ranks above another, and every connection between skills is soft: a skill still works when no skill answers its question. When a need misses the skill that should answer it, fix that skill's description, not the skill that asked. A need does not have to fire: inside a running skill Claude often answers the question itself, and that is fine. Do not add pressure to load a skill when Claude could answer; that was built and measured, the answers did not change, and it was rolled back (commit 0d6ad47 shows how it was done). `dev/routing/run.py` checks that a new prompt finds its skill; `dev/routing/session.py` checks needs inside a running skill.
- A skill does not announce that it loaded. Claude Code records each load as a `Skill` tool call in its transcripts; the evals read that record, and `dev/routing/usage.py` counts real use from it. A line that only says a skill is on shows that the model followed a format, not that the skill shaped the answer, and such lines compete for the top of the reply. A line at the top earns its place only when it shows me a guess I can correct, as the interview skill's lens and stake do.
- A skill lives in `plugins/yili-skills/skills/<name>/`. Keep development material out of that folder, because everything inside it is installed.
- Bump the version in both `plugins/yili-skills/.claude-plugin/plugin.json` and `.claude-plugin/marketplace.json` when a skill changes, or installed copies will not update.
- `.githooks/` holds a privacy guard that blocks private writing material from commits and pushes. Run `git config core.hooksPath .githooks` in a new clone. It needs `dev/write-like-myself/tools/local.toml`, which is not committed; without it only the pattern and path rules run.
- Every skill's README is at `dev/<skill>/README.md`.
- A change to a skill needs no eval case before it ships; a thought experiment on a real case is enough.
- Eval outputs stay on this machine: `.gitignore` keeps what a run writes (results, answers, judgings, build research) out of the repository. Commit the cases, the tools and a short write-up of what the run showed.
- Guidance that holds for the whole repository goes in this file, not in Claude's memory.
